# ToDo Manager — Complete Hackathon Project Documentation

Version: 1.0  
Prepared: October 16, 2026  
Status: Proposed project specification; implementation has not started.

## 1. Project overview

Build a responsive task management application that helps users capture work, prioritize it, track deadlines, and see progress. The project is intended for hackathon practice, with a small core that can be completed and demonstrated before adding optional features.

Working name: TaskFlow. This name is a placeholder, not a checked product or domain name.

### Problem

Tasks scattered across notes and messages are easy to forget. Users need one place to see what needs attention and what they have finished.

### Proposed solution

A personal dashboard with task creation, editing, completion, priorities, due dates, search, filters, and persistent storage.

### Assumptions and pending decisions

- Delivery platform: responsive web application, pending confirmation.
- The user's frontend, backend, database, and deployment stack are not yet supplied.
- Planning scenario: one developer and a 24-hour practice hackathon; adjust to the actual event.
- The core experience is a single-user demo. Account-based access is an optional extension with additional requirements below.
- No specific hackathon rules or judging criteria have been supplied.

## 2. Goals and scope

### Core MVP

1. Create tasks with a title, optional description, priority, and optional due date.
2. View saved tasks in a responsive list.
3. Edit task details.
4. Mark a task complete and reopen it.
5. Delete a task with a confirmation step.
6. Search by title or description.
7. Filter by status, priority, and overdue state.
8. Sort by creation date, due date, or priority.
9. Show total, pending, completed, and overdue counts.
10. Retain changes after reloading the application.

### Optional extensions, in suggested order

- User registration, login, logout, and private task ownership.
- Categories or tags.
- Kanban view with accessible move controls.
- Dark mode.
- Reminder notifications, requiring a scheduling and delivery service.
- Subtasks, recurring tasks, or collaboration.

### Outside the MVP

Team permissions, attachments, billing, calendar synchronization, AI features, recurring schedules, and push notifications are outside the first implementation.

## 3. Users and stories

Primary user: a student, developer, or individual managing daily work.

| ID | User story | Acceptance condition |
| --- | --- | --- |
| US-01 | As a user, I want to capture a task quickly. | A valid submission appears in the list and survives reload. |
| US-02 | As a user, I want to revise a task. | Saved edits appear everywhere the task is displayed. |
| US-03 | As a user, I want to track completion. | Completing or reopening a task updates its appearance and counts. |
| US-04 | As a user, I want to remove unwanted tasks. | Cancel leaves the task intact; confirmation removes it permanently. |
| US-05 | As a user, I want to find urgent work. | Filters and sorting consistently identify relevant tasks. |

## 4. Functional requirements

### Task rules

- Title: required; trim surrounding whitespace; 1–120 characters after trimming.
- Description: optional; up to 2,000 characters; plain text.
- Priority: `low`, `medium`, or `high`; default `medium`.
- Status: `pending` or `completed`; default `pending`.
- Due date: optional valid calendar date in `YYYY-MM-DD` format. Past dates are allowed.
- New tasks start pending. Completion sets `completedAt`; reopening clears it.
- `createdAt` is immutable; successful mutations update `updatedAt`.
- IDs and timestamps are generated by the persistence layer, not accepted from form input.
- Deleting a task is permanent after confirmation; no undo is required in the MVP.

### Search, filters, and ordering

- Search is case-insensitive across title and description, ignoring surrounding search whitespace.
- Status, priority, overdue, and search conditions combine using AND.
- A task is overdue when it is pending and its due date is before today's date in the user's browser timezone. A task due today is not overdue.
- Store due dates as date-only values; do not convert them to UTC timestamps.
- Store audit timestamps in UTC using ISO 8601 at the API boundary.
- Default order: newest created first.
- Due-date ascending: earliest first, undated tasks last.
- Priority descending: high, medium, low.
- Use creation time descending, then ID ascending, to resolve sorting ties.
- Dashboard counts use the full task collection; a separate visible-result count reflects filters.

### Failure handling

- Show inline field errors before submission and validate again at the backend if present.
- Prevent repeated submission while a mutation is in progress.
- Keep unsaved form values after a failed request.
- Show loading, empty, no-results, and network-error states separately.
- Confirm success only after persistence succeeds. A local-storage implementation must also handle write failures.

## 5. Screens and user experience

### Dashboard

Header with app name and Add Task button; summary cards; search; status and priority filters; overdue toggle; sort selector; task list; result count.

Each task shows title, priority text, due date when present, completion control, Edit, and Delete. Completed tasks remain readable with a distinct visual treatment. Priority and status must not depend on color alone.

### Create/edit task form

Fields: title, description, priority, due date. Actions: Save and Cancel. The same form can serve both creation and editing. Editing preloads current values. Cancel discards unsaved changes.

### Delete confirmation

Identify the selected task and state that deletion is permanent. Provide Cancel and Delete buttons, with initial focus on Cancel.

### Empty and error states

- No tasks: invite the user to create a first task.
- No matches: explain that filters returned no tasks and provide Clear Filters.
- Load failure: show a readable message and Retry.

### Responsive and accessible behavior

Use a single-column task layout on narrow screens, wrap toolbar controls, and avoid horizontal scrolling. Every input needs a visible label. All controls must work by keyboard and show focus. Dialogs should trap focus while open, close with Escape, and restore focus to the trigger. Announce mutation feedback to assistive technology. Honor reduced-motion preferences.

### Main flow

Open dashboard → Add Task → fill fields → validate → save → see task → edit or complete → filter/search → delete if needed.

### Full-stack design

Browser UI → HTTP API → validation and task service → database.

Keep UI components, domain rules, and storage access separate so that overdue logic and validation can be verified without rendering the entire application. Only the backend holds database credentials.

### Frontend-only alternative

Browser UI → task service → local storage.

Choose this only if it fits the user's stack or the practice objective. It has no server API, cross-device synchronization, or real account isolation. Handle malformed saved data and storage failures without silently overwriting existing records. The API section below is a proposed contract for the full-stack path.

## 7. Data model

### Task

| Field | Type | Rules |
| --- | --- | --- |
| id | UUID or database-native identifier | Primary key; generated |
| title | String | Required; 1–120 trimmed characters |
| description | String | Default empty string; max 2,000 characters |
| priority | Enum | low / medium / high |
| status | Enum | pending / completed |
| dueDate | Date or null | Date only |
| createdAt | UTC timestamp | Generated at creation |
| updatedAt | UTC timestamp | Updated on mutation |
| completedAt | UTC timestamp or null | Present only for completed tasks |
| userId | User identifier | Add only with account-based ownership |

For account support, a user owns many tasks. Enforce ownership in every task query and mutation. Use an index beginning with `userId` for account-scoped queries, then add indexes based on actual query needs. Use parameterized database operations and constraints for valid enums and required fields.

### Optional User

`id`, `name`, normalized unique `email`, `createdAt`, and an authentication-provider identifier or securely managed password hash. Never store plaintext passwords. Prefer the selected stack's established authentication integration.

## 8. Proposed REST API

Base path: `/api/v1`. JSON request and response bodies. This contract is a design proposal, not an implemented API.

| Method | Endpoint | Purpose | Success |
| --- | --- | --- | --- |
| GET | /tasks | Read tasks; optional search/status/priority/sort parameters | 200 |
| POST | /tasks | Create a task | 201 |
| GET | /tasks/:id | Read one task | 200 |
| PATCH | /tasks/:id | Update allowed fields or status | 200 |
| DELETE | /tasks/:id | Permanently delete a task | 204 |

For the small MVP, load all tasks and apply dashboard filters locally. `GET /tasks` without parameters returns the complete collection. If optional API filters are implemented, document them as `search`, `status`, `priority`, and `sort`, following the rules above. Calculate overdue locally using the user's calendar date. Do not add pagination until the client and aggregate counts support it coherently.

### Create request

```json
{
  "title": "Prepare hackathon demo",
  "description": "Practice the main user journey",
  "priority": "high",
  "dueDate": "2026-10-17"
}
```

### Task response

```json
{
  "data": {
    "id": "example-task-id",
    "title": "Prepare hackathon demo",
    "description": "Practice the main user journey",
    "priority": "high",
    "status": "pending",
    "dueDate": "2026-10-17",
    "createdAt": "2026-10-16T09:00:00Z",
    "updatedAt": "2026-10-16T09:00:00Z",
    "completedAt": null
  }
}
```

List responses use `{ "data": [] }`. PATCH accepts any nonempty subset of `title`, `description`, `priority`, `dueDate`, and `status`. `dueDate: null` clears the deadline. Reject unknown fields and client-supplied ownership, IDs, or audit timestamps. Invalid or empty updates return 400. Successful DELETE returns no body.

### Error format

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please correct the highlighted fields.",
    "fields": { "title": "A title is required." }
  }
}
```

Use 400 for invalid input, 401 for missing/invalid authentication when enabled, 404 for missing tasks or tasks outside the user's ownership, and 500 for unexpected server failures. Do not expose stack traces or secrets in responses. Define session endpoints only after selecting the authentication approach.

## 9. Security and privacy requirements

- Validate allowed fields, types, lengths, dates, and enum values at the server boundary.
- Render descriptions as plain text; avoid inserting untrusted HTML.
- Keep credentials in environment configuration and exclude local secrets from version control.
- Use HTTPS in deployment and restrict cross-origin access to intended clients.
- If cookie authentication is used, configure secure cookies and appropriate CSRF protection.
- With accounts, derive ownership from the authenticated session and test that another user cannot read, edit, or delete a task.
- A single-user backend without authentication must remain a local or deliberately public demo with synthetic data. Private multi-user deployment requires authentication and ownership enforcement.
- Do not log task descriptions, passwords, session tokens, or connection strings unnecessarily.

## 10. Quality targets

These are acceptance targets, not measured results.

- Complete core workflows at narrow mobile and desktop widths without horizontal overflow.
- Keep the dashboard responsive with 100 seeded tasks on a normal development machine.
- Persist successful changes across page reload and, for database storage, application restart.
- Show a visible loading state during pending requests and useful feedback on failure.
- Support the complete task lifecycle using keyboard input.
- Keep dates consistent around local midnight and avoid shifting date-only deadlines.

## 13. Verification plan

Use focused automated checks for domain rules and API boundaries, plus a short browser walkthrough for the user journey.

| Case | Expected result |
| --- | --- |
| Create with a valid title | Task appears and persists after reload |
| Submit blank or whitespace title | Rejected with a title error |
| Submit title/description at and above limits | Boundary accepted; excess rejected |
| Edit priority and clear due date | New priority persists; due date becomes null |
| Complete and reopen | Status, completion timestamp, and counts stay consistent |
| Cancel then confirm deletion | Cancel preserves task; confirm removes it |
| Search using mixed capitalization | Matching titles/descriptions are returned |
| Combine status and priority filters | Only tasks satisfying both appear |
| Deadline yesterday/today/tomorrow | Only yesterday's pending task is overdue |
| Completed task with a past deadline | Not counted as overdue |
| Sort with equal priority or no deadline | Ordering follows documented tie and null rules |
| Empty collection or zero search matches | Correct empty state appears |
| Save request fails | Form values remain; success is not falsely shown |
| Keyboard-only form/dialog use | Focus and controls remain usable |
| Account ownership, if enabled | A second user cannot access the first user's tasks |

### Definition of done

All core stories pass; no blocking task-lifecycle defects remain; secrets are excluded from the repository; fresh setup instructions work; sample data is available; and the intended demo environment has been checked. Record actual verification results during implementation rather than treating this specification as evidence of a passing build.
